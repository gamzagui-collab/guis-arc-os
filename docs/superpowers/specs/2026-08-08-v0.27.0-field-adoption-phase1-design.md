# GUI's Arc v0.27.0 Field Adoption Phase 1 설계

## 기준과 범위

- 공식 기준본: `GUI_Arc_Integrated_v0.25.1_Integrated.zip`
- 기준 SHA-256: `BC998AE8B2A751F83459AC983DEB84C15BE3FE9B7090556D2792577558AF4BB4`
- 기준 Commit: `5a04ee280c5b72fb578bc5f0bc247d4fda3daa15`
- v0.26.0 Voice 실험은 병합하지 않는다.
- Production은 변경하지 않는다.

이번 버전은 기존 Issue 업무 흐름을 바꾸지 않고 다음 두 기능만 추가한다.

1. Today 공사 작업에서 기존 `/issues/new`로 이동해 Issue를 등록한다.
2. 실제 Issue 담당자가 배정받은 업무에 최소 응답을 남긴다.

## WHY → GOAL → RISK → SOLUTION

### WHY

Today 작업과 Issue가 연결되지 않아 작업 정보를 다시 입력해야 하고, 관리자는 담당자가 배정을 확인했는지 구조적으로 알 수 없다.

### GOAL

- Construction/Today 원본을 복제하지 않고 Issue가 참조한다.
- 사용자가 본 최소 Context와 원본 item 근거를 보존한다.
- source 장애가 기존 Issue 등록을 막지 않는다.
- 담당 응답은 Issue 상태·조치·완료 Workflow와 분리한다.

### RISK

- 렌더링 순서를 영구 ID로 오인하면 revision 변경 후 다른 작업에 연결될 수 있다.
- stale source를 필수 조건으로 만들면 사진·위치·내용을 작성한 Issue 전체가 유실될 수 있다.
- timestamp만으로 최신 응답을 정하면 동일 시각 충돌 시 결과가 비결정적이다.
- 최소 응답이 별도 승인·기한·알림 Workflow로 확장될 수 있다.

### SOLUTION

- upload/plan 영구 ID와 bounded item refs를 저장하고 보수적으로만 재식별한다.
- 재식별 실패 시 source를 분리하고 일반 Issue를 HTTP 201로 저장한다.
- append-only 응답에 issue별 `response_revision`을 부여한다.
- 네 응답과 관리자 최소 표시 외 기능은 명시적으로 제외한다.

## 공사일보 source identity

### 확인된 안정성

`construction_daily_report_imported_items.id`는 한 upload revision 안에서는 영구 참조가 가능하다. 그러나 새 revision 확정 시 upload와 imported item 모두 새 UUID로 생성되므로 item ID는 revision 간 동일 작업 식별자가 아니다.

Today의 `construction-work-N`은 렌더 순서로 만든 임시 ID이므로 저장하거나 API 계약에 사용하지 않는다. 새 Work Package Entity도 만들지 않는다.

### source item refs

공사일보 Today 카드가 참조한 모든 imported item을 최소 JSON으로 보존한다.

```json
[
  {
    "itemId": "construction_daily_report_imported_items.id",
    "matchKey": "section_type|normalized_sheet_name|normalized_cell_range"
  }
]
```

- `itemId`는 Issue가 어떤 원본 작업들에서 만들어졌는지 추적하는 감사 근거다.
- SUPERSEDED upload와 item row가 보존되므로 과거 item 참조도 유지된다.
- `matchKey`는 새 revision에서 같은 원본 위치를 보수적으로 재식별하기 위한 값이다.
- 전체 row JSON, 인원 상세, 사용자·회사 개인정보는 복제하지 않는다.
- 배열 최대 100개, 직렬화 최대 16 KiB로 제한한다.
- 모든 matchKey가 최신 ACTIVE upload에서 각각 정확히 한 건과 일치할 때만 최신 item ID로 재연결한다.
- 하나라도 0건 또는 2건 이상이면 유사 내용이나 렌더 순서로 추정하지 않고 재식별 실패로 처리한다.

이 source reference 계약은 v0.27.1 금일 작업진도와 v0.27.2 계획/실적/Issue 연결에서도 동일 작업 추적에 재사용한다.

## 데이터 구조

### Issue source reference

```text
issue_source_references
- issue_id TEXT PRIMARY KEY REFERENCES issue_items(id) ON DELETE CASCADE
- site_id TEXT NOT NULL REFERENCES sites(id)
- source_type TEXT NOT NULL
- source_id TEXT NOT NULL
- source_revision INTEGER NOT NULL
- work_date TEXT NOT NULL
- source_item_refs_json TEXT NOT NULL DEFAULT '[]'
- source_snapshot_json TEXT NOT NULL
- created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

허용 source type:

```text
CONSTRUCTION_DAILY_REPORT
CONSTRUCTION_MONTHLY_PLAN
```

snapshot은 `workDate`, 표시용 `company`, `trade`, `workDescription`, `location`만 저장한다. 전체 공사일보 JSON을 저장하지 않는다. 월간계획은 영구 plan ID와 revision을 source로 사용하고 item refs는 빈 배열이다.

### 담당 응답

```text
issue_assignee_responses
- id TEXT PRIMARY KEY
- issue_id TEXT NOT NULL REFERENCES issue_items(id) ON DELETE CASCADE
- site_id TEXT NOT NULL REFERENCES sites(id)
- response TEXT NOT NULL
- note TEXT
- actor_user_id TEXT NOT NULL REFERENCES users(id)
- response_revision INTEGER NOT NULL CHECK(response_revision >= 1)
- responded_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
- UNIQUE(issue_id, response_revision)
```

허용 응답은 다음 네 개뿐이다.

```text
ACKNOWLEDGED
NOT_MY_RESPONSIBILITY
DUE_DATE_DISCUSSION
BLOCKED
```

`NOT_MY_RESPONSIBILITY`와 `BLOCKED`는 1~500자 메모가 필수다. 응답은 Issue status, Issue revision, 담당자, due date, 조치·완료 Workflow를 변경하지 않는다.

현재 응답은 `ORDER BY response_revision DESC LIMIT 1`로만 판정한다. `responded_at`은 표시·감사 시각일 뿐 최신 순서 판정에 사용하지 않는다. 클라이언트가 현재 `responseRevision`을 제출하면 Worker가 현재 최대값과 비교하여 `+1`을 삽입한다. 동일 revision 경쟁은 unique constraint와 충돌 응답으로 결정적으로 차단한다. 별도 상태 snapshot table은 만들지 않는다.

## Today에서 Issue 등록

Today 작업 카드의 주 액션 영역에 `이슈 등록`을 추가한다. 기존 Issue 생성 capability가 있을 때만 노출한다.

```text
/issues/new?sourceType={type}&sourceId={id}&sourceRevision={revision}
```

URL에는 회사명·작업내용·위치 같은 업무 문자열을 넣지 않는다. Issue form-options 또는 전용 source-context 조회가 현재 site에서 source를 다시 읽는다. 기존 `/issues/new` 화면, 사진·위치·내용 필수 계약, SpeechRecognition 경로는 유지한다.

공종 표시 문자열로 canonical ID를 추측하지 않는다. 정확한 회사·공종 ID가 있을 때만 제안값을 제공한다. source의 위치는 참고 Context로 표시하되 기존 Issue 위치 선택은 유지한다.

## stale source fallback 계약

source 연결은 optional enhancement이며 기존 Issue 등록의 single point of failure가 아니다.

1. Worker가 현재 site 범위에서 source와 최신 ACTIVE revision을 재조회한다.
2. 공사일보는 제출된 모든 matchKey가 최신 revision에서 각각 정확히 한 item과 일치하면 최신 upload ID·revision·item ID 목록·snapshot으로 `RELINKED`한다.
3. 월간계획은 동일한 영구 plan ID가 존재하고 revision만 증가했다면 최신 revision·snapshot으로 `RELINKED`한다.
4. source 없음, 다른 site, 잘못된 type, item match 누락·중복, ref 상한 초과 또는 source 조회 실패이면 source relation을 저장하지 않고 `DETACHED`한다.
5. `DETACHED`에서도 기존 Issue 필드와 media가 유효하면 HTTP 201로 Issue를 생성한다.
6. 응답은 `sourceLinkStatus: "DETACHED"`와 `sourceLinkWarning: "원본 작업 연결을 확인하지 못해 일반 이슈로 등록했습니다."`를 반환한다.
7. 다른 site source의 존재 여부는 구분하지 않고 같은 일반 경고만 반환한다.
8. 유효 source는 `LINKED`, source query가 없으면 `NONE`을 반환한다.

Issue, media, 선택적 source reference, idempotency와 Audit은 한 DB batch로 기록한다. media 저장 뒤 DB batch가 실패하면 기존 R2 cleanup을 수행한다. source resolver 실패는 source만 분리하며 Issue·사진·위치·내용 저장은 계속한다.

Issue 상세 source 조회 실패도 Issue 상세·조치·완료 요청·완료·Root Cause API를 실패시키지 않으며 저장 당시 snapshot을 사용한다.

## 담당 응답 권한과 API

Worker와 UI는 하나의 순수 capability 함수를 공유한다.

```text
선택 현장과 Issue 현장 일치
AND ISSUE Board access가 EDIT 또는 MANAGE
AND issue.act permission 보유
AND 로그인 userId가 현재 assigned_to_user_id와 일치
AND Issue status가 COMPLETED 또는 CANCELLED가 아님
```

역할 이름을 hard-code하지 않는다. `issue.manage_all` 사용자도 다른 담당자를 대신해 응답하지 않는다.

```text
POST /api/v1/issues/{issueId}/assignee-response
```

CSRF, Context version, site scope, board access, idempotency를 기존 Issue 경계에서 재사용한다. 성공 시 `ASSIGNEE_RESPONSE_CHANGED` Audit에 이전·신규 응답과 response revision을 기록한다.

## 관리자 최소 표시

- Issue 목록·상세에 최신 응답을 한국어 badge로 표시한다.
- Today Issue Provider에는 `응답 확인 필요 N건` 최소 집계만 추가한다.
- 확인 필요 응답은 `NOT_MY_RESPONSIBILITY`, `DUE_DATE_DISCUSSION`, `BLOCKED`다.
- 별도 Dashboard, 통계, 알림은 만들지 않는다.

## Migration

`database/migrations/0033_field_adoption_phase1.sql`에 두 테이블과 필요한 site·issue·최신 응답 index만 추가한다. 기존 Issue·Construction·Root Cause 데이터를 수정하거나 backfill하지 않고 기존 table을 DROP/RECREATE하지 않는다.

## 실패·오류 계약

- source 관련 오류: Issue가 유효하면 `201` + `DETACHED` 일반 Issue fallback
- 응답 권한 없음: `403 ISSUE_ASSIGNEE_RESPONSE_DENIED`
- 완료·취소 Issue: `409 ISSUE_ASSIGNEE_RESPONSE_STATE_INVALID`
- 응답 메모 누락: `400 ISSUE_ASSIGNEE_RESPONSE_NOTE_REQUIRED`
- 응답 revision 충돌: `409 ISSUE_ASSIGNEE_RESPONSE_REVISION_CONFLICT`

응답 저장 중에는 버튼을 비활성화하고 `aria-busy=true`와 한국어 처리 중 문구를 표시한다. 성공하면 최신 badge를 갱신한다. 실패하면 입력을 보존하고 재시도 경로를 제공한다. Idempotency-Key로 중복 응답을 방지한다.

## 실패 테스트 계약

1. imported item ID가 새 공사일보 revision에서 재발급됨을 고정한다.
2. aggregate 카드가 모든 원본 item ID·matchKey를 보존하고 렌더링 ID를 저장하지 않는다.
3. 모든 match가 유일하면 최신 revision으로 `RELINKED`된다.
4. 0건·중복 match, 범위 위반, ref 상한 초과, 조회 실패이면 source만 `DETACHED`되고 Issue는 201로 저장된다.
5. detached 응답이 source 존재 여부를 노출하지 않고 한국어 경고를 반환한다.
6. source 없는 직접 Issue 생성, 사진, 위치, SpeechRecognition, 배정·조치·완료·Root Cause 계약이 불변이다.
7. 네 담당 응답이 append-only로 기록된다.
8. 동일 `responded_at`에서도 `response_revision`으로 최신값이 결정된다.
9. stale response revision과 동시 동일 revision 쓰기가 결정적으로 차단된다.
10. 실제 담당자만 응답 가능하고 관리자 대리 응답, 다른 현장·회사, 완료·취소 Issue는 차단된다.
11. 응답은 Issue status·revision·담당자·due date를 변경하지 않는다.
12. 관리자 최소 badge·집계만 표시되고 제외된 Workflow·상태가 없다.

검증 우선순위는 단위 테스트, API 권한 Matrix, 자동 Browser E2E, 실제 모바일 계정 1회다.
