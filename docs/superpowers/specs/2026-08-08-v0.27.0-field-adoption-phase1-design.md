# GUI's Arc v0.27.0 Field Adoption Phase 1 설계

## 기준과 범위

- 공식 기준본: `GUI_Arc_Integrated_v0.25.1_Integrated.zip`
- 기준 SHA-256: `BC998AE8B2A751F83459AC983DEB84C15BE3FE9B7090556D2792577558AF4BB4`
- 기준 Commit: `5a04ee280c5b72fb578bc5f0bc247d4fda3daa15`
- v0.26.0 Voice 실험은 병합하지 않는다.
- Production은 변경하지 않는다.

이번 버전은 기존 Issue 업무 흐름을 바꾸지 않고 다음 두 기능만 추가한다.

1. Today 공사 작업에서 기존 `/issues/new`로 이동해 Issue를 등록한다.
2. 실제 Issue 담당자가 배정받은 업무에 최소 응답을 남긴다.

## WHY

Issue는 독립적으로 현장 사용이 가능하지만 Today의 실제 공사 작업과 연결되지 않아 사용자가 작업 정보를 다시 입력해야 한다. 또한 담당자는 배정 사실을 확인했는지, 담당 업무가 아닌지, 기한 협의나 작업 장애가 필요한지 구조적으로 알릴 수 없다.

## GOAL

- 기존 Construction/Today 원본을 복제하지 않고 Issue에 참조한다.
- 등록 당시 사용자가 본 최소 Context를 snapshot으로 보존한다.
- source가 사라지거나 조회에 실패해도 Issue는 독립적으로 표시하고 처리한다.
- 담당자 응답은 Issue status, 조치, 완료 요청 및 완료 Workflow와 분리한다.
- 기존 직접 Issue 등록, 사진, SpeechRecognition, 배정, 조치, 완료, Root Cause 및 권한 계약을 보존한다.

## 현재 데이터 원본

### 확정 공사일보

- 원본: `construction_daily_report_uploads`
- 영구 ID: `id`
- 날짜: `work_date_kst`
- revision: `revision`
- Today 사용 조건: `parse_status='CONFIRMED' AND status='ACTIVE'`
- 작업 행: `construction_daily_report_imported_items`

Today는 여러 작업 행을 `aggregateMajorWorks()`에서 합칠 수 있다. 화면의 `construction-work-N`은 렌더링 순서로 생성되는 임시 ID이므로 source ID로 저장하지 않는다. 확정 공사일보 카드는 상위 공사일보 upload ID와 revision을 source로 저장하고, 카드별 표시 내용은 snapshot으로 구분한다.

### 월간계획 fallback

- 원본: `construction_monthly_plans`
- 영구 ID: `id`
- revision: `revision`
- 업체, 공종, 위치, 작업 내용과 예정 인원을 보유한다.

월간계획 카드는 plan ID와 revision을 source로 저장한다.

### Work Package

신규 Work Package Entity는 만들지 않는다. 기존 공사일보 upload와 월간계획 ID가 원본 역할을 담당한다.

## Source Reference 구조

작은 1:1 relation table을 사용한다.

```text
issue_source_references
- issue_id TEXT PRIMARY KEY REFERENCES issue_items(id) ON DELETE CASCADE
- site_id TEXT NOT NULL REFERENCES sites(id)
- source_type TEXT NOT NULL
- source_id TEXT NOT NULL
- source_revision INTEGER NOT NULL
- work_date TEXT NOT NULL
- source_snapshot_json TEXT NOT NULL
- created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

허용 source type:

```text
CONSTRUCTION_DAILY_REPORT
CONSTRUCTION_MONTHLY_PLAN
```

snapshot은 다음 값만 저장한다.

```json
{
  "workDate": "YYYY-MM-DD",
  "company": "표시용 업체명 또는 null",
  "trade": "표시용 공종명 또는 null",
  "workDescription": "작업 내용",
  "location": "위치 또는 null"
}
```

전체 공사일보 JSON, 인원 상세, 사용자 이름, 전화번호와 인증정보는 저장하지 않는다.

## Today에서 Issue 등록

Today 작업 카드의 펼침 영역에 `이슈 등록` 버튼을 추가한다. 버튼은 기존 Issue 생성 capability가 있을 때만 표시한다.

이동 형식:

```text
/issues/new?sourceType={type}&sourceId={id}&sourceRevision={revision}
```

URL의 회사명, 작업 내용이나 위치 문자열은 신뢰하지 않는다. Issue form-options와 생성 API가 현재 site Context에서 source를 다시 조회한다.

등록 화면은 기존 `/issues/new`를 그대로 사용한다.

- 작업 내용은 편집 가능한 참고값으로 제공한다.
- canonical 업체·공종 ID를 정확히 확인할 수 있을 때만 선택값을 제안한다.
- 공종 표시 문자열을 보고 ID를 추측하지 않는다.
- source 위치는 참고 Context로 표시하고 기존 Issue 위치 선택은 유지한다.
- 사진·위치·내용 필수 계약을 완화하지 않는다.
- query가 없거나 source 해석이 실패하면 기존 직접 등록 화면으로 안전하게 fallback한다.

생성 요청에서 Worker는 source site와 revision을 다시 확인한다. revision이 달라졌으면 `409 ISSUE_SOURCE_REVISION_STALE`로 현재 Context를 다시 불러오도록 안내한다. source가 유효하면 Issue 생성, media, source reference, idempotency와 Audit을 한 batch로 기록한다. media 저장 이후 DB batch가 실패하면 기존 R2 cleanup을 그대로 수행한다.

## Source 표시와 장애 격리

Issue 상세 응답은 source reference와 snapshot을 포함한다.

- 원본 조회 성공: 최신 원본 정보와 등록 당시 snapshot을 함께 표시한다.
- 원본 취소·삭제·조회 실패: snapshot만 표시한다.
- source 오류는 Issue 상세, 조치, 완료 요청, 완료 및 Root Cause API를 실패시키지 않는다.
- source revision 변경은 기존 Issue snapshot을 덮어쓰지 않는다.

## 담당자 응답

응답 이력을 append-only table로 저장한다.

```text
issue_assignee_responses
- id TEXT PRIMARY KEY
- issue_id TEXT NOT NULL REFERENCES issue_items(id) ON DELETE CASCADE
- site_id TEXT NOT NULL REFERENCES sites(id)
- response TEXT NOT NULL
- note TEXT
- actor_user_id TEXT NOT NULL REFERENCES users(id)
- responded_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

허용 응답:

```text
ACKNOWLEDGED
NOT_MY_RESPONSIBILITY
DUE_DATE_DISCUSSION
BLOCKED
```

응답이 없으면 API와 UI에서 `NONE`으로 표현한다. 변경할 때 기존 행을 수정하거나 삭제하지 않는다. 가장 최근 행이 현재 응답이다.

메모 계약:

- `ACKNOWLEDGED`: 선택
- `NOT_MY_RESPONSIBILITY`: 1~500자 사유 필수
- `DUE_DATE_DISCUSSION`: 선택
- `BLOCKED`: 1~500자 사유 필수

응답은 Issue status, Issue revision, 담당자, due date, 조치와 완료 Workflow를 변경하지 않는다.

## 응답 권한

공통 순수 capability 함수를 Worker와 UI가 함께 사용한다.

```text
선택 현장과 Issue 현장 일치
AND ISSUE Board access가 EDIT 또는 MANAGE
AND issue.act permission 보유
AND 로그인 userId가 현재 assigned_to_user_id와 일치
AND Issue status가 COMPLETED 또는 CANCELLED가 아님
```

역할 이름을 hard-code하지 않는다. `issue.manage_all`도 다른 담당자를 대신한 응답을 허용하지 않는다. 관리자는 기존 배정·조치·완료 관리 기능을 계속 사용한다.

쓰기 API는 CSRF, Context version, site scope, board access와 idempotency를 기존 Issue 경계에서 재사용한다.

```text
POST /api/v1/issues/{issueId}/assignee-response
```

성공 시 `ASSIGNEE_RESPONSE_CHANGED` Audit에 이전 응답과 신규 응답을 기록한다.

## 관리자 최소 표시

- Issue 목록과 상세에 최신 응답을 한국어 badge로 표시한다.
- Today Issue Provider에는 `응답 확인 필요 N건` 한 항목만 추가한다.
- 확인 필요 응답은 `NOT_MY_RESPONSIBILITY`, `DUE_DATE_DISCUSSION`, `BLOCKED`다.
- 별도 Dashboard, 알림 엔진과 통계 체계는 만들지 않는다.

## Migration

`0033_field_adoption_phase1.sql`을 추가한다.

- 위 두 table과 site·issue·최근 응답 index만 추가한다.
- 기존 Issue와 Construction 데이터를 수정하거나 backfill하지 않는다.
- 기존 table을 DROP 또는 RECREATE하지 않는다.
- Engine Core와 Root Cause schema를 변경하지 않는다.
- Migration 재실행 안전성은 프로젝트의 기존 적용 계약에 맞춰 검증한다.

## 오류 처리

- 잘못된 source type: `400 ISSUE_SOURCE_TYPE_INVALID`
- 다른 현장 source: `403 ISSUE_SOURCE_SCOPE_DENIED`
- source 없음: `404 ISSUE_SOURCE_NOT_FOUND`
- source revision 변경: `409 ISSUE_SOURCE_REVISION_STALE`
- 응답 권한 없음: `403 ISSUE_ASSIGNEE_RESPONSE_DENIED`
- 완료·취소 Issue: `409 ISSUE_ASSIGNEE_RESPONSE_STATE_INVALID`
- 응답 메모 누락: `400 ISSUE_ASSIGNEE_RESPONSE_NOTE_REQUIRED`

Today source Context 로딩 실패는 기존 `/issues/new` 사용을 막지 않는다. 응답 저장 실패는 기존 Issue 조치 기능을 비활성화하지 않으며 입력한 메모를 보존하고 재시도를 제공한다.

## 사용자 액션 피드백

- `이슈 등록` 링크는 기존 페이지 이동이므로 중복 mutation이 없다.
- 응답 저장 중 버튼을 비활성화하고 `aria-busy=true`와 한국어 처리 중 문구를 표시한다.
- 성공 시 최신 badge와 이력을 즉시 갱신한다.
- 실패 시 선택 응답과 메모를 보존하고 한국어 오류와 재시도 경로를 제공한다.
- Idempotency-Key로 중복 응답 기록을 방지한다.

## 테스트 전략

먼저 기존 동작 Characterization Test를 고정한다.

- source 없는 직접 Issue 생성
- 사진과 기존 SpeechRecognition 계약
- 배정, 조치, 완료 요청, 완료
- Root Cause와 권한 격리

신규 테스트:

1. Today 확정 공사일보와 월간계획 source Context
2. source reference와 제한된 snapshot 저장
3. source 없는 직접 Issue
4. source 삭제·미조회와 revision 변경 후 snapshot 유지
5. 다른 현장 source 차단
6. 네 가지 담당자 응답과 append-only 이력
7. 응답 변경 Audit와 idempotency
8. 실제 담당자만 응답 가능
9. 관리자 대리 응답 차단
10. 완료·취소 Issue 응답 차단
11. 응답이 Issue status와 revision을 변경하지 않음
12. 응답 실패가 기존 action Workflow를 변경하지 않음
13. Today 최소 집계와 Issue badge
14. source 기능 실패 시 기존 `/issues/new` fallback

검증 우선순위는 Unit, API 권한 Matrix, 자동 Browser E2E, 대표 모바일 계정 1회다.
