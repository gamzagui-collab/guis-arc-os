# 공사일보 엑셀·출력일보 사진 보관 계약

## 공식 원본

- 공사일보의 공식 원본은 현장 관리자가 업로드하고 확인·확정한 회사 보고용 `.xlsx` 파일이다.
- 지원 양식 `URBANTREE_DAILY_V2`는 `공 사 일 보` 제목과 `공 종`, `출력현황`, `전일 작업사항`, `금일 작업예정사항` 헤더 조합으로 날짜 블록을 식별한다. 67행 반복은 실제 양식의 검증 정보일 뿐 유일한 탐색 조건이 아니다.
- 선택 날짜와 문서 날짜가 다르거나 등록 양식과 일치하지 않으면 저장·확정하지 않는다.
- 월간 파일의 모든 날짜 블록을 분석하고 최신 확정본과 날짜별 정규화 해시를 비교해 `NEW`, `UNCHANGED`, `CHANGED`, `WARNING`, `INVALID`, `FUTURE` 상태를 반환한다.
- 병합 셀의 좌상단 값과 수식 셀의 저장된 계산값을 읽는다. 계산값이 없을 때는 안전하게 참조할 수 있는 단순 `이전 날짜 셀 + 1`만 처리하며 그 외에는 `FORMULA_DATE_UNRESOLVED` 경고를 남긴다.
- 합계·자재·장비·사진대지 영역을 주요 작업으로 취급하지 않는다.
- 원본 파일은 R2에 비공개 저장하고 메타데이터·파싱 결과·Revision은 D1에 저장한다.

## 월간 파일 업로드

- `.xlsx` 원본은 최대 50MB까지 허용하며 확장자, MIME, ZIP 시그니처, 파일 크기와 SHA-256을 검증한다.
- 브라우저는 권한 검사로 생성된 15분짜리 업로드 세션의 presigned PUT URL로 비공개 R2에 직접 업로드한다. 원본 전체는 Construction Worker API 요청 본문을 통과하지 않는다.
- 업로드 경로는 현장·사용자·세션에 바인딩하고 다른 사용자나 현장에서는 완료·확정할 수 없다.
- 분석 완료 시 검증된 원본을 새 비공개 경로로 고정하고 임시 객체를 삭제한다. 만료되거나 검증에 실패한 임시 객체도 삭제한다.
- 날짜별 정규화에는 현장, 날짜, 원본 현장명, 날씨·기온, 공종별 전일·금일·누계 인원, 전일·금일 작업 원문, 비고와 작업 순서를 포함한다. 파일명과 셀 위치는 비교에서 제외한다.
- `NEW` 날짜만 D1 Batch로 자동 반영하고 `UNCHANGED`에는 Revision을 만들지 않는다. `CHANGED`는 변경 필드 비교 후 사용자가 명시적으로 승인할 때만 새 Revision을 만든다.
- `WARNING`, `INVALID`, `FUTURE`는 자동 반영하지 않는다. 명시적인 휴무·작업 없음은 유효한 일보로 처리하되 실제 빈 블록은 확인 대상으로 남긴다.
- 자동 반영과 변경 승인은 작업별 멱등성 키를 별도 기록한다. 동일 요청 재전송은 기존 결과를 반환하며 중복 Revision을 만들지 않는다.
- 과거 날짜 업로드를 허용한다. Today는 오늘 날짜의 최신 확정본만 사용한다.
- 월간 분석 세션의 D1 JSON은 확정에 필요한 전체 Parser 분석과 Preview 요약만 저장한다. 날짜별 Preview는 저장된 분석과 최신 Revision에서 다시 계산하며, Parser 분석과 동일한 작업 항목을 Preview에 중복 저장하지 않는다.
- D1 저장 직전 SQL·binding의 내용이 아닌 자료형과 UTF-8 바이트 크기만 진단한다. D1 한도를 넘으면 통제된 한국어 오류로 중단하고 임시 R2 원본을 유지해 다시 업로드할 수 있게 한다.
- 검증 R2 원본은 D1 분석 저장이 성공한 뒤에만 임시 원본을 정리한다. 저장 실패 시 새 검증 객체를 제거하며, 만료된 실패 세션 정리 시 임시·검증 경로를 함께 정리한다.

## 실제 양식의 데이터 한계

- 제공된 양식에는 회사명 열이 없다. 공종과 금일 작업예정사항, 공종별 금일 예정 인원만 추출한다.
- 출력현황 공종과 금일 작업 공종은 원문, 표시문자 제거 정규화명, 등록 별칭, 복수 핵심 단어 순으로 비교한다. 핵심 단어 하나만 일치하는 경우에는 자동 연결하지 않는다.
- `전기통신설비공`과 `전기통신공`은 등록 별칭으로 연결하며 출력인원을 한 번만 적용한다. 원문 공종명과 매칭 근거는 별도 메타데이터로 보존한다.
- 출력인원은 있으나 대응 작업이 없으면 원본 공종명, “노코멘트”, `OUTPUT_WORKFORCE_FALLBACK` 출처를 가진 보완 항목으로 저장한다.
- 금일 총 출력인원은 직원 계열의 실제 숫자와 개별 공종 금일 인원을 합산한다. 합계·총계 행은 더하지 않고 검증값으로만 비교하며 불일치 시 경고를 남긴다.
- 회사명을 추측하거나 공종명을 회사명으로 바꾸지 않는다. `companyName=null`, `companyBreakdownAvailable=false`로 반환하고 “회사별 인원 정보가 원본 공사일보에 없습니다.” 경고를 표시한다.
- 자유서술 작업내용에서 위치를 임의 분해하지 않고 원문을 보존하며 `WORK_TEXT_UNCERTAIN` 경고를 남긴다.
- 빈 인원은 `null`, 실제 숫자 0은 `0`, 숫자로 해석할 수 없는 값은 `null`과 `WORKFORCE_INVALID`로 보존한다.
- 추출값에는 원본 시트·행·셀 범위, 원문, 정규화값, 경고 코드를 함께 제공한다.
- Today의 인원은 실제 출역이 아니라 공사일보에 기록된 예정 인원이다.

## 출력일보 사진 보관

- 기존 전자식 출력일보 UI는 사용자 메뉴에서 제거하며 기존 DB와 API는 호환 이력으로 보존한다.
- 출력일보는 날짜·회사·업로드 사용자·시각·메모와 원본·썸네일 사진으로 보관한다.
- 다른 현장 접근은 차단하고 협력업체 사용자는 본인 회사 범위만 조회·등록한다.
- 잘못 등록한 자료는 물리 삭제하지 않고 사유와 처리자를 남겨 무효 처리한다.
- OCR, AI 판독, 이름·작업·인원 자동 확정 기능은 구현하지 않는다.

## Today

- 오늘 날짜의 `ACTIVE` 상태인 최신 `CONFIRMED` Revision만 사용한다.
- 동일 작업명은 묶고 위치는 중복 제거한다.
- 회사 정보가 있는 데이터만 회사별 예정 인원 합계를 표시한다. 원본에 회사 정보가 없으면 총 예정 인원만 표시하고 회사 목록을 만들지 않는다.
- 미확정·분석 중·분석 실패·조회 실패·작업 없음·예정 인원 없음 상태를 각각 구분한다.

## v0.17.0 현재 현장 공종 매칭

- 공종 매칭 기준은 범용 건설 사전이 아니라 제공된 현재 현장 코퍼스와 실제 공사일보에서 확인된 표기만 사용하는 `SITE` 범위다.
- 원문, 정규화 표기, 표준 공종 ID, 매칭 유형, 신뢰도, 한국어 판단 근거, 원본 셀 위치를 함께 보존한다.
- 전기통신, 콘크리트, 견출, 내장목공, 난간대, 도시가스, 목창호의 확인된 현장 별칭만 자동 연결한다. 기계·전기, 일반·소방, 미장·견출, 직원·직영, 형틀·내장목공 등 충돌 관계는 자동 연결하지 않는다.
- 괄호가 붙은 복합 공종은 기본 공종으로 연결하되 괄호 안 숫자는 검증 근거로만 사용한다. 공식 예정 인원은 항상 왼쪽 출력현황의 금일 인원이다.
- 한 출력현황 행은 한 공종 그룹에 한 번만 배정하며, 강한 근거가 약한 근거보다 우선한다. 동률 또는 충돌은 자동 확정하지 않고 검토 경고로 남긴다.
- 공종 단위 검토 경고와 총계 불일치는 날짜 전체 저장을 막지 않는다. 날짜, 필수 머리글, 행 구조처럼 문서를 식별할 수 없는 오류만 날짜 단위 자동 반영을 막는다.
- Today는 `공종명(인원) - 작업내용` 형식을 사용한다. 인원이 비어 있으면 0으로 바꾸지 않고 `인원 확인 필요`를 표시하며, 출력현황만 있는 공종은 `노코멘트`로 보완한다.

## v0.17.1 공종 규칙 데이터 분리

- 표준 공종·별칭·핵심어는 `trade-data/site-trade-dictionary.js`, 충돌 관계는 `trade-data/site-trade-conflicts.js`를 공식 원본으로 사용한다.
- `trade-matcher.js`는 공식 데이터를 읽어 기존 v0.17.0과 동일한 매칭 정책을 적용하며 공종·별칭·충돌 목록을 중복 정의하지 않는다.
- 공식 데이터는 모듈 초기화 시 한 번 무결성을 검사한다. 표준 ID, 정규화 별칭, 충돌 관계 중복과 잘못된 참조를 발견하면 명확한 오류로 중단한다.
- 운영 절차는 `docs/32_SITE_TRADE_DICTIONARY.md`를 따른다.
# v0.19.4 사용자 확정·Revision 계약 복구

- 분석 완료 뒤 날짜 카드는 `NEW`와 `CHANGED`만 선택할 수 있다. `UNCHANGED`, `REVIEW_REQUIRED`, `WARNING`, `INVALID`, `FUTURE`는 확정 선택을 차단한다.
- 화면은 선택 날짜를 신규와 변경으로 나누어 기존 `AUTO_NEW`, `CONFIRM_CHANGED` 계약을 호출한다.
- `AUTO_NEW`에 날짜 목록이 있으면 그 신규 날짜만 처리하고, 날짜 목록이 없는 기존 호출은 모든 신규 날짜 처리 동작을 유지한다.
- 확정은 기존 활성본을 `SUPERSEDED`로 바꾸고 다음 Revision을 `CONFIRMED`·`ACTIVE`로 생성한다. 동일 비교 결과에는 새 Revision을 만들지 않는다.
- DB, Migration, Parser, 공종 매칭 엔진, 비교 엔진 및 R2 저장 계약은 변경하지 않는다.

# v0.19.5 기존 분석 세션 확정 계약

- 신규 분석 직후와 `최근 월간 업로드 → 날짜별 내용 보기`는 같은 확정 Preview 렌더러와 제출 함수를 사용한다.
- 기존 `ANALYZED` 세션과 일부 날짜가 확정된 `CONFIRMED` 세션 모두 날짜별 최신 `comparisonStatus`를 다시 계산한다. 세션 상태만으로 전체를 읽기 전용 처리하지 않는다.
- `NEW`와 `CHANGED`만 선택할 수 있고 나머지 상태는 읽기만 가능하다. 조회 전용 사용자는 모든 체크박스와 확정 제어를 표시하지 않는다.
- NEW·CHANGED 동시 선택은 각각 `AUTO_NEW`, `CONFIRM_CHANGED`로 요청한다. 그룹별 요청 확인값을 별도로 만들고 일부 실패를 전체 성공으로 표시하지 않는다.
- 성공 또는 부분 성공 뒤 세션 상세 API를 다시 조회해 서버 Revision과 `UNCHANGED` 상태를 표시한다. 실패 날짜는 다시 선택할 수 있다.
- 기존 분석 세션과 R2 원본을 재사용하므로 파일 재업로드가 필요 없다. DB·Migration·R2 구조는 변경하지 않는다.
- Integration에는 배포하지 않았고 Production은 변경하지 않았다.

# v0.19.6 confirm D1 크기 계약

- 실제 Integration의 `SQLITE_TOOBIG`는 confirm batch에서 갱신된 월간 전체 객체를 `construction_daily_report_upload_sessions.analysis_json`에 다시 쓰던 UPDATE binding에서 발생했다.
- 31일 회귀 fixture의 최초 축약 `analysis_json`은 1,571,000바이트였고, 조회용 날짜 Preview를 붙인 객체는 3,061,583바이트였다. D1의 단일 TEXT·BLOB·row 2,000,000바이트 제한을 넘는다.
- confirm은 최초 `analysis_json`을 변경하지 않는다. 세션 상태와 확정 시각만 저장하고 날짜별 비교 상태는 상세 조회 시 기존 Revision으로 다시 계산한다.
- 날짜별 `content_snapshot_json`, `trade_match_json`, workforce warning, action result와 Audit은 의미를 유지한다. 회귀 fixture의 실제 저장 JSON 최댓값은 content snapshot 19,369바이트다.
- 다중 날짜는 기존 한 action batch로 처리하며 batch가 실패하면 Revision, imported items, Audit, action과 세션 상태가 함께 롤백된다. NEW·CHANGED가 별도 요청인 기존 UI에서는 그룹별 부분 성공을 그대로 안내한다.
- 기존 v0.19.3~v0.19.5 세션과 R2 원본은 재업로드나 변환 없이 사용할 수 있다.
- 신규 Migration과 기존 Migration 변경은 없으며 Integration에는 배포하지 않았고 Production은 변경하지 않았다.

# v0.19.7 날짜 확정 UX 계약

- 월간 상세의 `전체 선택`, `전체 해제`, `선택 날짜 확정`은 App Shell 고정 헤더 아래 sticky 도구로 유지하며 현재 선택한 확정 가능 날짜 수를 함께 표시한다.
- NEW와 CHANGED 날짜에만 `이 날짜 확정`을 제공한다. 개별 확정도 기존 공통 제출 함수와 `AUTO_NEW`·`CONFIRM_CHANGED` 계약을 사용하며 별도 API를 만들지 않는다.
- 개별·일괄 확정은 공통 실행 잠금을 사용한다. 처리 중 모든 확정 제어를 비활성화하며 실패 시 선택 가능 상태와 한국어 오류 안내를 복원한다.
- 성공 또는 부분 성공 뒤 세션 상세를 다시 조회한다. 성공한 날짜만 선택에서 제거하고 나머지 선택, 펼친 상세 영역, 스크롤 위치를 보존한다.
- 조회 전용 사용자는 확정 도구·체크박스·개별 확정 버튼을 볼 수 없으며 기존 서버 EDIT 권한 검증을 유지한다.
- 신규 Migration은 없고 Integration에는 배포하지 않았으며 Production은 변경하지 않았다.
